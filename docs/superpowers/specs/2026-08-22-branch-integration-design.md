# 분산 브랜치 안정 반입 설계

## 목적

2026-07-20~22에 `mint-agentic`과
`claude/mint-scene-context-refactor-xtph5u`에서 진행된 작업 중, 현재 `main`의
제품 철학과 아키텍처에 맞고 회귀를 독립적으로 검증할 수 있는 부분만 반입한다.

완료 상태는 “두 브랜치를 병합했다”가 아니라 다음 세 결함이 서로 독립된 커밋으로
해소된 상태다.

1. 조기 종료된 MLX 생성 태스크가 다음 GPU 작업과 겹치지 않는다.
2. 동일 사건 키가 사건 그래프·플롯 분석을 깨뜨리지 않는다.
3. 반복 대사가 있는 원고에서도 기록된 대화가 엉뚱한 첫 대사로 재앵커되지 않는다.

## 현재 상태와 위험

- `main`은 `origin/main`보다 1커밋 앞서 있고, 현재 관찰 시점에 `PLAN.md`,
  `Sources/MINTCore/Editor/CompletionController.swift`,
  `Sources/MINTCore/SidebarView.swift`, `Sources/MINTCore/Storage/EntryStore.swift`에
  사용자 미커밋 작업이 있다. 실행 직전 `git status`를 다시 확인해야 한다.
- `mint-agentic`은 `claude/mint-scene-context-refactor-xtph5u`의 조상이다.
  두 브랜치를 각각 병합할 이유가 없다.
- 후자 브랜치는 공통 조상 이후 88개 파일, 약 14,150줄을 추가하고 포맷 일괄
  변경까지 포함한다. 텍스트 자동 병합이 되더라도 최신 `main`의 의미를 보존한다고
  볼 수 없다.
- `7057c92`는 현재 `main`의 `3f1c1d3`과 패치 동등하므로 반입 대상이 아니다.

## 선택한 통합 방식

### 채택: 현재 main 위에서 동작 단위 재구현

원본 커밋은 근거와 테스트 아이디어로만 사용한다. 구현은 현재 타입·캐시 정책·문서
구조를 기준으로 다시 작성한다. 한 결함당 하나의 커밋을 만들고 각 커밋은 단독으로
`swift test`와 `swift build`를 통과해야 한다.

이 방식은 cherry-pick보다 손이 더 들지만 다음을 보장한다.

- `e50b649`의 과거 KV 처리로 현재 `6338676`을 되돌리지 않는다.
- KeyScene·Agent·자동 대화 기록 같은 미승인 기능이 함께 들어오지 않는다.
- 실패한 단계만 되돌릴 수 있고 앞서 통과한 수정은 유지할 수 있다.
- PLAN의 최신 모델 측정과 현재 스키마를 과거 문서로 덮지 않는다.

### 기각: 브랜치 전체 merge

변경 범위가 너무 크고 포맷 변경이 실제 동작 변경을 가린다. Git 충돌 수가 적다는
사실은 안전성 근거가 아니다. 자동 병합된 구형 코드가 최신 로직을 의미상 되돌릴 수
있다.

### 기각: 커밋 단위 cherry-pick

후보 커밋들이 Agent, KeyScene, 서술 시점, UI와 서로 의존하고 한 커밋 안에도 여러
성격의 변경이 섞여 있다. 특히 `e50b649`, `44ad6b2`, `6a4f518`은 유용한 수정과
현재 반입하면 안 되는 기능을 함께 담고 있다.

## 반입 단위

### A. 사건 키 중복 방어

출처는 `6a4f518`의 `EventParser` 중복 제거와 `44ad6b2`의
`uniqueEventsForAnalysis`다.

- 한 씬의 모델 출력에서 같은 사건 줄이 반복되면 첫 사건만 저장한다.
- 사건 그래프와 플롯 스레드에 넘기는 목록은 `stableKey`별 첫 사건만 유지하고
  40개 상한을 적용한다.
- 메모 해시도 실제 분석 입력과 같은 정규화 목록으로 계산한다.
- `StoryEvent.stableKey` 형식과 사이드카 스키마는 바꾸지 않는다.

### B. 대화 기록 재앵커

출처는 `44ad6b2`의 `ConversationDetector.reanchor` 개선이다.

- 저장 범위와 콘텐츠 해시가 여전히 맞으면 탐색 없이 기존 기록을 반환한다.
- 첫 대사가 여러 번 나오면 과거 `utf16Start`에 가장 가까운 후보를 선택한다.
- 마지막 대사도 예상 종료 위치에 가장 가까운 후보를 선택한다.
- 첫 줄이나 마지막 줄을 확정하지 못하면 `nil`로 처리한다. 과거 길이만큼 임의로
  늘리는 폴백은 제거한다.
- Enter로 사용자가 기록을 승인하는 현재 UX는 유지한다. 자동 기록 전환은 하지 않는다.

### C. MLX 생성 태스크 종료 동기화

출처는 `e50b649`다.

- `TokenIterator`와 `MLXLMCommon.generateTask()`로 스트림과 내부 Task를 함께 얻는다.
- 폴더 이름, 백그라운드 one-shot, 자동완성의 세 생성 경로는 스트림 소비가 끝나면
  내부 Task에 `cancel()`하고 `task.value`를 기다린다.
- 모델 교체는 이전 컨테이너의 `perform`이 끝난 뒤 시작한다.
- 자동완성 캐시는 내부 Task 종료를 기다린 뒤 commit하고 `cacheInUse = false`로
  내려, 이후 부모 취소가 이미 안전한 캐시를 abandon하지 않게 한다.
- 현재 `6338676`의 원칙—협조 취소는 commit, 실제 오류는 abandon—은 유지한다.

## 검증 및 병합 순서

현재 진행 중인 저장 비동기화와 폴더 이름 생성 취소 작업을 먼저 사용자 소유의
커밋으로 확정한다. 특히 폴더 이름 Task 취소는 MLX 내부 생성 Task 종료와 직접
맞닿으므로, 이 작업이 빠진 과거 HEAD를 통합 기준으로 삼지 않는다. 계획 문서 자체의
untracked 상태는 허용하지만 기존 추적 소스의 미커밋 변경이 남아 있으면 실행을
시작하지 않는다.

위험이 작은 결정적 수정부터 병합한다.

1. 사건 키 중복 방어
2. 대화 기록 재앵커
3. MLX 생성 태스크 종료 동기화

각 단계는 별도 `fix/` 브랜치 또는 격리 worktree에서 구현하고, 테스트·빌드·리뷰가
끝난 뒤에만 다음 단계로 간다. 세 단계를 한 PR이나 한 커밋으로 묶지 않는다.

MLX 수정은 모델 없는 단위 테스트와 실제 Metal 스트레스 검증을 둘 다 요구한다.
릴리즈 MINTBench에서 취소 직후 다음 생성을 20회 반복하고, 전체 프로세스를 다시
10회 실행해 EXIT=11이 한 번도 없어야 한다. 한 번이라도 실패하면 PLAN의 부채를
해소로 표시하지 않고 해당 수정은 main 반입을 중단한다.

## 이번 통합에서 제외하는 작업

- Writing Agent와 trace (`efe32ad`, `f1c5da0`): 현재 예측 엔진 범위 밖이며 모델
  지연 근거가 부족하다.
- KeyScene 전체 (`44ad6b2`): P0-A 구현은 있으나 토큰당 예측 품질 측정이 없다.
- 전역 서술 시점·한국어 이름 정규화 (`e5bee10`): 호명 대상을 화자명으로 연결하는
  반례가 있어 실코퍼스 재설계가 선행돼야 한다.
- 동백꽃 Agent·대화 보강 전체 (`6a4f518`): 한 작품 고유 표현이 결정 규칙에
  하드코딩돼 있다. 범용 따옴표 스캐너는 별도 설계 후보로만 남긴다.
- 포맷·린트 일괄 변경 (`4195940`): 기능 반입과 분리해야 하며 이번 범위가 아니다.
- 과거 PLAN/README 전체: 현재 문서에 필요한 측정 결과와 설계 결정만 새로 기록한다.

이 제외 항목은 폐기가 아니라 격리다. 각 기능은 별도 설계와 MINTBench 품질 게이트를
통과한 뒤 독립적으로 재검토한다.

## 완료 조건

- 세 수정이 각각 독립 커밋이며 외부 브랜치 merge commit이 없다.
- `swift test`와 `swift build`가 각 커밋에서 통과한다.
- 사건 중복과 반복 대화 재앵커의 모델 없는 회귀 테스트가 추가된다.
- MLX 취소 스트레스 20회와 프로세스 반복 10회가 모두 성공한다.
- 기존 KV 캐시 수학 테스트와 리플레이 웜 재사용 수치가 회귀하지 않는다.
- PLAN에는 실제 검증 명령과 결과만 기록한다.
- Agent, KeyScene, 자동 대화 기록, 스키마 변경은 diff에 포함되지 않는다.
