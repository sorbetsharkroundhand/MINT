# 씬 분할 — 설계 & 구현 (PLAN §16-3 해소)

> **구현 완료 (2026-07-17)** — `DocumentOutline`에 §2 설계 그대로:
> `sentencePieces`(문장 바닥) → `capOversized`(어절·강제 폴백) →
> `segmentRanges`(CDC, FNV-1a — **프로세스 안정 해시 필수**: `Hasher`는 실행마다
> 시드가 달라 경계가 흔들려 매 실행 전체 재요약이 된다). §5의 커서 거리순
> 순회도 함께 (컨트롤러 캐럿 기록 → 인덱서 `caretProvider`).
> 스키마 버전은 **안 올렸다** — 디코딩 모양 불변이고, 미분할 씬(≤1500)의
> 해시가 그대로라 기존 요약이 살아남는다. 구 대형 씬의 고아 키는 기존
> pruning GC가 청소한다 (버전을 올리면 멀쩡한 요약까지 버린다).
> 검증: `SceneSplitTests` 12건 — §3의 타일링 무손실(개행·공백 꼬리 포함),
> 상한 보장, 종결부호·공백 없는 원고 폴백, 경계 안정성(같은 입력=같은 해시,
> 끝 편집이 앞 세그먼트 불변), 소수점 비경계.

장편에서 지식 파이프라인이 원고의 대부분을 보지 못하는 문제의 설계.
측정은 전부 실제 저널(「위대한 개츠비」 88,187자 · 「날개」 22,521자)로 했다.

## 1. 문제 재규정 — "헤딩 없는 원고" 문제가 아니다

PLAN §16-3에 처음 "헤딩 없는 원고의 씬 분할"로 적었으나 **오진이었다.**

| 원고 | 헤딩 | 현재 씬 | 씬 크기 | 이해 범위 |
|---|---|---|---|---|
| 「날개」 | 1개 | 1개 | 22,522자 | **6.7%** |
| 「위대한 개츠비」 | **7개** | 7개 | 10 / 17,642 / 12,434 / 17,068 / 16,320 / 12,433 / 12,281자 | **10.2%** |

개츠비는 `# 제1장`…`# 제6장`으로 **제대로 나뉘어 있는데도 90%를 잃는다.**
진짜 원인은 헤딩 유무가 아니라 이것이다:

> **씬 크기에 상한이 없는데 이해 상한(`maxSceneCharacters = 1500`)은 있다.
> 넘는 만큼은 조용히 사라진다.**

`BackgroundIndexer.runPass`가 씬 원문을 `.prefix(maxSceneCharacters)`로 자른다.
자른 사실은 어디에도 기록되지 않는다 — 요약도 사건도 앞 1,500자만 보고 만들어지고,
사용자는 AI가 9장을 읽었다고 믿는다. **조용한 실패**라서 더 나쁘다.

따라서 PLAN §16-3의 선택지 중 (a)헤딩 없을 때만 폴백 · (c)헤딩 권유는 개츠비를
못 고친다. **(b) 긴 씬을 상한 단위로 쪼갠다**가 유일하게 근본을 고친다.

## 2. 설계

### 2.1 씬 = 헤딩 경계 **그리고** 크기 상한을 함께 지키는 단위

- 헤딩은 항상 씬을 연다 (기존 유지 — PLAN §8 "골격 = 사용자의 헤딩 구조").
- 헤딩 본문이 상한을 넘으면 **여러 씬(세그먼트)으로 쪼갠다**. 같은 `headingPath`를
  공유하고 `segmentIndex`로 구분한다 → "제1장 (3/14)".
- `scenes` 배열 순서 = 담화 순서 = **Pos v1 그대로**. Pos의 의미는 바뀌지 않는다.

### 2.2 바닥 단위는 문장

문단(블록)으로는 부족하다 — 개츠비의 최장 블록은 **17,060자**다(각 장이 사실상
개행 없는 한 줄). 문장이 안전한 바닥 단위임을 확인했다:

| 원고 | 문장 수 | 중앙값 | 최장 | 1500자 초과 |
|---|---|---|---|---|
| 개츠비 | 2,546 | 23자 | 162자 | **0** |
| 날개 | 642 | 35자 | 185자 | **0** |

경계는 종결부호(`.!?…`) + 닫는 따옴표(선택) + 공백. 한국어 문장은 종결어미가
있어 이 규칙으로 충분하다 — 형태소 분석 불요 (PLAN §16-7과 같은 논지).

**폴백 사슬** (종결부호가 없는 원고·붙여쓴 텍스트 대비):
문장 → 어절(공백) → 강제 절단. 이 사슬이 없으면 "종결부호 없는 4,000자"가
씬 1개(4,000자)가 되어 잘림이 되돌아온다 — 시뮬레이션에서 확인했다.

### 2.3 경계는 위치가 아니라 **내용**으로 정한다 (CDC)

단순 누적(greedy)은 앞쪽 한 글자가 경계를 밀어 **뒤 세그먼트가 연쇄로 더티**가
된다. 내용 정의 청킹(content-defined chunking)은 문장 **자신의 해시**로 경계를
정하므로 편집의 영향이 국소에 갇히고 다음 경계에서 재동기화된다.

```
누적 ≥ MIN 이고  hash(문장) % 8 == 0  → 여기서 끊는다
누적 + 다음 문장 > MAX               → 강제로 끊는다 (상한 보호)
```

**측정 — 한 글자 삽입 시 재요약되는 씬 수** (250회, 동일 시드):

| 원고 | 전략 | 씬 수 | 평균 | 중앙 | p95 | 최악 |
|---|---|---|---|---|---|---|
| 개츠비 (헤딩 7) | greedy | 110 | 1.24 | 1 | 1 | **14** |
| 개츠비 | **cdc(1/8)** | 87 | 1.17 | 1 | 2 | **9** |
| 개츠비 | cdc(1/16) | 78 | 1.10 | 1 | 1 | 7 |
| 날개 (헤딩 0) | greedy | 28 | **1.94** | 1 | 2 | **23** |
| 날개 | **cdc(1/8)** | 22 | 1.20 | 1 | 2 | **9** |
| 날개 | cdc(1/16) | 18 | 1.08 | 1 | 1 | 11 |

**정직하게**: 중앙값은 둘 다 1이고 평균 차이는 작다. CDC의 이득은 **꼬리**와
**헤딩 없는 원고**에 몰려 있다 — 날개에서 greedy 최악 23은 전체 28개 중 82%가
한 글자에 재요약된다는 뜻이고, 이는 CLAUDE.md §2-3("증분이 기본, 전체 재처리는
복구 수단")의 위반이다. 헤딩이 있는 개츠비에서 차이가 작은 이유는 헤딩이 연쇄를
장 안에 가두기 때문 — 즉 greedy의 안전성은 사용자가 헤딩을 쓰는지에 의존한다.
그 의존을 없애는 것이 이 설계의 요점이다.

### 2.4 파라미터

```
MIN_CHARS = 800     // 이보다 작으면 끊지 않는다 (토막 씬 방지)
MAX_CHARS = 1500    // = maxSceneCharacters — 넘지 않으므로 잘림이 사라진다
divisor   = 8       // 경계 확률 1/8 (문장당)
```

`1/8` 선택 근거: 여유 구간 [800, 1500] = 700자 ≈ 20문장에서 경계를 못 찾을
확률이 `(7/8)^20 ≈ 7%`다 (1/16이면 28%). 강제 절단이 적을수록 내용 정의의
성질이 살아난다. 1/16은 씬 수가 10%쯤 적어 LLM 비용이 싸다 — **비용이 문제가
되면 먼저 만질 손잡이**다.

결과: 개츠비 87씬(평균 1,014자·최대 1,475) · 날개 22씬(평균 1,024자·최대 1,489).
**이해 범위 10.2% → 100% · 6.7% → 100%. 상한 초과 0.**

## 3. 구현 규칙 (시뮬레이션에서 다친 곳)

- **세그먼트를 문자열 쪼개기로 만들지 말 것.** 반드시 원문에 대한
  `utf16Range`로 정의해 문서를 빈틈없이 타일링한다. 시뮬레이터에서 블록을
  쪼갰다 이어붙이며 **헤딩 사이 개행을 유실**했다(개츠비만 실패, 날개는 블록이
  하나라 안 걸림). 기존 `DocumentOutline.parse`가 이미 오프셋 기반이니 그 방식을
  유지하면 구조적으로 불가능해진다.
- **공백뿐인 꼬리도 버리지 말 것.** `if cur.strip()` 같은 가드가 원문을 먹는다.
- 세그먼트 이어붙이기 == 원문을 **테스트로 고정**한다 (원고 유실 = 최악의 버그).

## 4. 파급 (기존 자산과의 정합)

| 대상 | 영향 |
|---|---|
| `Pos` = scenes 배열 인덱스 | **무변경** — 세그먼트도 담화 순서로 배열에 들어간다 |
| `contentHash` 앵커 | 세그먼트 원문의 해시. 사건·요약 키가 그대로 동작 |
| 톰스톤 (`save(pruningTo:)`) | **무변경** — 편집된 세그먼트만 고아가 된다 |
| `ContextAssembler.knowledgeText` | **무변경** — `utf16Range` 비교라 그대로. 같은 장의 씬이 많아져 근→원 삭감이 실제로 일한다 |
| 장·작품 요약 전파 | **개선** — 「날개」가 씬 1개라 `scenes.count >= 2` 조건에 걸려 장·작품 요약이 없었다. 이제 22씬 → 피라미드가 살아난다 |
| 타임라인 UI | 라벨에 `segmentIndex` 필요 — "날개 (3/22)". 미이해 구간 경고는 사라진다 |
| 저널·짧은 문서 | **무변경** — 상한 미만이면 씬 1개 (엣지 케이스로 확인) |

## 5. 비용 — 정면으로 볼 것

이해 범위 10% → 100%의 대가는 **LLM 호출 수**다.

- 개츠비: 씬 7개 → **87개**. 요약 87회 + 사건 추출 87회 = **174회**.
- 날개: 1개 → 22개 → 44회.

깊은 패스는 유휴·게이트·메모이제이션이 걸려 있어 일회성이지만, air(16.9GB MoE)에서
호출당 2~4초면 개츠비 한 편에 **10분 이상의 백그라운드 연산**이다.

그래서 **커서 근처 우선 처리가 이 설계의 일부다.** 현재 `runPass`는
`for scene in outline.scenes` — 문서 순서다. 씬이 87개가 되면 사용자가 6장을
쓰는 동안 인덱서가 1~5장을 먼저 갈아 정작 필요한 지식이 마지막에 온다.
깊은 패스의 순회를 **커서 거리순**으로 바꾼다 (인덱서에 캐럿 제공자 배선 필요 —
`CompletionController`가 캐럿을 안다).

## 6. 기각안

- **greedy 누적**: §2.3 측정 — 헤딩 없는 원고에서 최악 23/28 재요약. 안전성이
  사용자의 헤딩 습관에 의존한다.
- **헤딩 없을 때만 폴백** (PLAN §16-3 (a)): 개츠비(헤딩 7개, 10.2%)를 못 고친다.
- **헤딩 권유** (동 (c)): 사용자에게 도구의 한계를 떠넘긴다. 게다가 개츠비는
  이미 헤딩을 쓴다.
- **문단(블록) 단위 분할**: 개츠비 최장 블록 17,060자 — 바닥 단위로 부족.
- **maxSceneCharacters를 크게**: 프리필은 취소 불가 구간이라 이 길이가 "타이핑
  재개 → 예측 대기"의 최악 지연을 정한다 (BackgroundIndexer 주석). 지연을 팔아
  이해를 사는 거래 — CLAUDE.md §3 "UX를 늦추는 쪽으로 풀지 않는다" 위반.

## 7. 미해결 / 위험

- **요약 품질이 씬 크기에 어떻게 반응하는지 미측정.** 1,000자 → 120자(8:1)가
  적정한지는 모델을 태워 봐야 안다. 파라미터는 구조(파급·상한)로 정했지 품질로
  정하지 않았다 — air 벤치와 함께 재측정할 것.
- 씬이 10배가 되면 B 블록 후보도 10배 — `knowledgeText`의 근→원 삭감이 실제로
  동작하기 시작한다. 예산 600자에 씬 요약 5개면 5,000자 분량의 맥락. 적정한지
  리플레이 벤치로 확인 필요.
- CDC 경계는 문장 해시에 의존 → **문장 하나를 고치면 그 문장이 경계였다가
  아니게 될 수 있다.** 이때 두 세그먼트가 합쳐지며 최악 9까지 나온다. p95는 2라
  일상 편집에서는 드물다.
- 스키마 v3 필요 (씬 정의가 바뀌어 기존 해시가 전부 무효) — 파생 캐시라
  폐기·재구축이면 끝이지만, 위 174회 재구축 비용이 한 번 발생한다.
