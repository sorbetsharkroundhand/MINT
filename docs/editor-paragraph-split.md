# 긴 문단 나누기 — 설계 (에디터 성능)

거대 문단이 유발하는 타이핑 랙의 해소안. 측정·근거는 [editor-perf.md](editor-perf.md).

## 문제 (측정으로 확정)

에디터(TextKit 1)는 **문단 하나를 레이아웃의 최소 단위**로 쓴다 — 문단 안 글자
하나가 바뀌면 그 문단 전체의 줄바꿈을 다시 계산한다. 그래서 키 입력 비용이
문서 길이가 아니라 **커서가 든 문단의 크기**에 비례한다.

| 원고 | 최대 문단 | 키 입력 1회 | IME 3자모 |
|---|---|---|---|
| 메밀꽃 필 무렵 | 455자 | 0.34ms | 1.0ms |
| 날개 | 470자 | 0.45ms | 1.4ms |
| **위대한 개츠비** | **17,061자** | **6.74ms** | **20.2ms** |

22k 날개가 멀쩡하고 88k 개츠비만 랙인 것이 증거다 — 길이 비례가 아니라 문단
크기 비례(15배 차이). 개츠비의 한 장은 348개 문장이 문단 나눔 없이 붙은
**17k자 단일 문단**이다(번역 텍스트 붙여넣기로 문단 구분이 사라진 형태).

serialize·TextKit 레이아웃 **둘 다** 문단 크기에 비례하므로, serialize만 고쳐선
반만 해결된다. 근본 해소는 **문단을 정상 크기로 나누는 것**뿐이다 — TextKit 1에
문단을 안 나누고 레이아웃 단위만 쪼갤 방법은 없다(문단 경계는 텍스트의 개행으로만
정의된다).

## 원칙 — 왜 자동 실행이 아닌가

문단 나누기는 **원문을 수정한다**(개행 삽입). 요약·바이블 같은 파생 캐시가 아니다.
CLAUDE.md의 두 불변식이 곧장 걸린다:

- **§2-1 원문이 유일한 진실** — 원문 변경은 조용히 하지 않는다.
- **§1-5 사용자 수정이 자동 추출을 이긴다** — AI가 원고 모양을 임의로 못 바꾼다.

따라서 인물 감지 깔때기(§7)와 같은 규율을 따른다: **감지는 자동, 실행은 사용자
확인.** 조용히 원고를 바꾸는 순간 이 기능은 신뢰를 잃는다.

## 안전 보장 (실행 시 지키는 것)

1. **글자는 하나도 바뀌지 않는다** — 삽입·삭제·재배치 없이 **문단 구분 개행만**
   추가한다. 실측: 개츠비 17k 문단 → 7조각, 삽입된 문자는 개행 32개뿐, 나머지
   글자 완전 동일.
2. **문장 중간은 절대 자르지 않는다** — 종결부호(`. ! ? …`) + 닫는 따옴표 뒤
   공백에서만 나눈다. 목표 크기 근처에 문장 경계가 없으면(병적으로 긴 한 문장)
   그 구간은 안 나눈다.
3. **한 번의 되돌리기로 원상복구** — 전체를 단일 undo 그룹으로 실행. `⌘Z` 한 번.
4. **문서의 기존 문단 스타일을 따른다** — 개츠비는 문단을 빈 줄(`\n\n`)로 구분하므로
   새 경계도 `\n\n`으로 넣는다(시각적 일관성).
5. **거절은 기억한다** — "그대로 두기"를 고르면 그 문서에선 다시 묻지 않는다
   (거부 목록, §7과 같은 패턴).

## 파라미터 (측정 유도, 튜닝 가능)

```
TRIGGER = 6000   // 이 크기를 넘는 문단만 나누기 제안 (IME 3자모가 예산 절반 초과 시작)
TARGET  = 2500   // 이 크기로 누적해 문장 경계에서 끊는다 (2500자 ≈ 키당 0.7ms)
MIN_TAIL = 800   // 마지막 조각이 이보다 작으면 앞 조각에 합친다 (토막 방지)
```

TRIGGER를 6000으로 둔 이유: 5000자(1.1ms·IME 3.3ms)는 아직 쾌적해 굳이 안 나눈다 —
과도한 분할로 원고 모양을 흔들지 않는다. 실측상 개츠비 전체에서 대상 문단은 4개뿐.

## 알고리즘 (결정적·LLM 없음, CLAUDE.md §2-5)

지식 파이프라인의 씬 분할(docs/m6-scene-split.md)과 **문장 경계 검출을 공유**하되
목적이 다르다:

| | 씬 분할(§6) | 문단 나누기(이 문서) |
|---|---|---|
| 대상 | 파생 지식(요약용) | **원문** |
| 가시성 | 보이지 않음 | 사용자에게 보임 |
| 경계 방식 | 내용 정의(CDC — 증분 안정성) | **단순 누적(greedy)** |
| 트리거 | 백그라운드 자동 | 사용자 확인 |

문단 나누기는 **일회성 사용자 편집**이라 증분 안정성이 필요 없다 → CDC 대신 단순
누적이 맞다(더 단순, 결과가 예측 가능). 문장 경계 검출만 공유 헬퍼로 뺀다
(`SentenceSplitter`).

```
문단마다:
  길이 ≤ TRIGGER → 건드리지 않음
  아니면:
    문장 조각으로 나눔 (종결부호+공백 경계, 경계 공백 유지)
    조각을 누적해 ≥ TARGET에서 끊음
    마지막 조각이 < MIN_TAIL이면 직전에 합침
    조각들을 "\n\n"으로 이어 원문단을 대체 (단일 undo 그룹)
```

## UX — 감지·설명·확인

인물 감지(§7)와 같은 비모달 배너. **설명이 이 기능의 핵심**이다 — 사용자는 왜
원고에 손을 대는지, 무엇이 바뀌는지, 되돌릴 수 있는지를 알아야 동의한다.

**배너(에디터 상단, 해당 문서에 TRIGGER 초과 문단이 있고 거절 안 했을 때):**

> ⚡ 아주 긴 문단이 있어 빠르게 입력하면 끊길 수 있어요.
> [문단 나누기]  [자세히]  [그대로 두기]

**[자세히] 펼침:**

> 에디터는 문단 하나를 통째로 다시 배치하기 때문에, 문단이 길수록 글자 하나
> 입력에 드는 비용이 커져요. 이 문서에서 가장 긴 문단은 약 **17,000자**로, 보통
> 문단의 **30배가 넘어요**.
>
> **문장 경계에서** 이 문단을 몇 개로 나누면 입력이 다시 매끄러워져요. **글자는
> 하나도 바뀌지 않고**, 문단 사이에 빈 줄만 들어가요. 마음에 안 들면 **⌘Z 한
> 번으로 되돌릴 수 있어요.**
>
> 나눌 문단: **4개** · 문장 중간은 자르지 않아요.

**실행 후(조용한 확인, 잠시 뒤 사라짐):**

> 긴 문단 4개를 문장 경계에서 나눴어요. ⌘Z로 되돌리기

숫자(17,000·30배·4개)는 감지 결과에서 채운다 — 막연한 안내가 아니라 **이 문서의
실제 수치**를 보여줘야 신뢰가 선다.

## 구현 배치 (CLAUDE.md §4)

- `SentenceSplitter`(신규, `Sources/MINTCore/Knowledge/` 또는 공용) — 결정적 문장
  경계. 씬 분할과 공유.
- 감지: `BlockTextView` 또는 배경 인덱서에서 문단 크기 스캔(O(문서), 열 때/유휴에
  1회 — 키 입력 경로 아님).
- 실행: `BlockTextView`에 `splitOversizedParagraphs()` — 단일 undo 그룹으로 storage
  편집. 직렬화 캐시는 자동 무효화(구조 변화 → 전체 재구축, 이미 처리됨).
- 거부 목록: `JournalEntry`에 문서별 플래그(인물 `rejectedCharacterNames`와 같은 자리).
- UI 문자열은 한국어, 색·폰트는 `Theme` 토큰(CLAUDE.md §4).

## 검증 (구현 완료 2026-07-16 · `swift test` 21건)

- **텍스트 보존(최우선)**: 순수 로직·에디터 편집 양쪽에서 `개행 제거한 원문 ==
  개행 제거한 결과`. 실제 개츠비 원고 포함. 원고 유실은 되돌릴 수 없다.
- 문장 중간 미절단, `⌘Z` 단일 그룹으로 원문 정확 복원, 병적 케이스(경계 없는
  초장문장은 안 나눔), 코드 블록 제외, 나눈 뒤 편집·증분 캐시 정합.
- **전후 지연(실측)**: 개츠비 키 입력 중위 **6.82ms → 1.97ms (3.5배)**. 4개 문단
  나눔 → 커서 문단이 작아져 TextKit 레이아웃·serialize 둘 다 감소. IME 3자모도
  ~6ms로 예산 안.

## 구현 노트 (설계에서 확정된 것)

- **`\n\n` 삽입은 `insertText` + 단일 undo 그룹** — 뒤 문단·뒤 오프셋부터 처리해
  앞 오프셋 보존. 새 문단은 typingAttributes를 물려받아 `.p` 유지.
- **감지는 문서 로드 때 1회**(`refreshLongParagraphDetection`) — 키 입력 경로에
  O(문서)를 안 넣는다. 세션 중 문단이 6000자를 넘기는 건 드물고 점진적이라
  다음 로드에 잡힌다.
- **UI**: 툴바에 조용한 표시(대상 있을 때만 나타남) → 클릭 시 `LongParagraphNotice`
  팝오버. 숫자는 감지 실제 수치. 다리는 `CompletionController`의 클로저
  (`knowledgeProvider`와 같은 패턴).
- 거부 목록은 **미구현** — 지금은 "그대로 두기"가 팝오버만 닫는다(다음 로드에
  표시 재등장). 반복이 거슬리면 §7처럼 문서별 플래그 추가.

## 한계 (정직하게)

- 나누는 위치는 **크기 기반 문장 경계**지 저자의 의미 단위가 아니다 — 진짜 문단
  나눔은 저자만 안다. 그래서 사용자 확인 + 되돌리기 + "그대로 두기"가 필수다.
- 이미 나눈 문단을 사용자가 다시 이어 붙여 거대 문단을 만들면 재감지된다
  (거부 목록으로 반복 질문은 막는다).
